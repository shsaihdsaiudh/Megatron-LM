# 实验 B 结果：GEMM 与 NCCL all-gather 的 SM 竞争（1 节点，8×H20）

- 数据：`eb_default.json`、`eb_ctas4.json`、`eb_ctas16.json`（各 10 次重复，表中为各 rank 中位数的最大值）；
  `eb_nsys.json` 与 `nsys/eb_T1024.rank0.nsys-rep`（仅 T=1024，3 次重复，只有 rank 0，计时受 profiling 影响）。
- 环境：torch 2.14.1+cu130，NCCL 2.30.7（torch 报告的版本）。

## 检查

- 四个日志的 `[eb] world=8 ...` 头行分别显示 NCCL_MAX_CTAS = default、4、16、default，与文件名一致。
- 日志中没有 NCCL 错误或警告。只有 torch 的 SM carveout 警告，该功能被标为临时实验性功能，可能随时移除。
- nsys 运行与 sweep 的同配置结果接近：ag_delay 差异不超过 2.3%，fsdp chain 差异不超过 1%。

## 结论

1. H1 只部分成立。AG 确实在 GEMM 尾部启动：有 GEMM 运行的 AG 全部在 GEMM 进度 ≥0.6 时启动，中位进度 0.86–0.89。
   但 carveout 没有消除这段等待。T=1024、默认 CTAS 下，AG 启动等待均值从 carveout 0 的 0.39 ms 变为 carveout 16 的 0.45 ms，p90 从 0.89 ms 升到 1.11 ms。
2. 独立模式的 ag_delay（约 1.0 ms）中，约 40% 是启动等待，约 60% 是 AG 在与计算重叠时变慢。重叠时 AG 时长均值为独立时的 1.8 倍（carveout 16 时为 2.0 倍）。后一项包含等待其他 rank 的时间，单 rank trace 无法拆开。
3. carveout 降低了 chain_overhead，但让整链变慢。相对 carveout 0 的 fsdp 净增量（默认 CTAS）：T=256 为 +1.3 ms（c8）和 +4.2 ms（c16），T=1024 为 +3.4 ~ +3.6 ms 和 +12.9 ms，T=4096 为 +1.2 ~ +1.6 ms 和 +20.4 ms。GEMM 本身在 c8 下慢 9–17%，在 c16 下慢 25–31%，抵消了通信开销的下降。
4. 优先级没有可测收益。多数配置下 normal 与 high 的 ag_delay 中位数差在 0.1 ms 以内，最大差 0.27 ms（默认 CTAS、T=4096、c8，high 更差）。T=1024、c16 时 high 更差（ag_delay 1.44 对 1.35 ms）。nsys 中 high 的启动等待更长（0.46 对 0.39 ms），但 AG 时长更短，两者大致抵消。
5. NCCL_MAX_CTAS=4 是唯一在整链上有明显收益的设置，但只在 T=4096 时有效。T=4096、carveout 0 时 chain 为 138.4 ms，比默认的 147.8 ms 少 9.4 ms（−6%）。rank 0 的 rep 间 sd 为 0.4 ms（ctas4）和 1.3 ms（默认），因此该差异显著。在 T=256 和 T=1024 时 CTAS=4 更差：T=1024 为 50.6 对 42.2 ms，原因是单独运行 AG 从 0.74 ms 增至 2.73 ms。CTAS=16 在 T=4096 时减少 5.4 ms，在 T=1024 时与默认持平（c0 为 42.4 对 42.2 ms）。
6. 口径注意：fsdp 的 chain_overhead 定义为 chain − gemm_alone，包含有 AG 重叠时 GEMM 的变慢，不只是通信暴露。T=1024、carveout 0 时，重叠 rank 的 nvjet 核时间为 40.6 ms，gemm_alone 为 31.9 ms（+27%），与 chain 增量 9.4 ms 接近。两者仅相差约 1 ms，因此这部分开销主要来自 GEMM 被拖慢。

## 异常

- 启动等待的分布是双峰的。约一半 AG 几乎没有等待，另一半约 0.9 ms。因此中位数接近 0，不能代表平均情况。表 3 同时给出均值和比例。
- 每个 rep 的第一个 AG 有 0.2–1.2 ms 的启动等待，即使单独运行也是如此。它来自每次 synchronize 之后的 CPU 发射延迟，与 GEMM 无关。
- CTAS=4 下 AG 单独运行为 2.73 ms（默认 0.74 ms，CTAS=16 为 0.78 ms）。因此 ag_delay 的基线随 CTAS 变化，不能跨文件直接比较，应比较整链时间（表 2）。
- T=256 时 CTAS=16 比默认多 0.7 ms（c0 为 16.9 对 16.2 ms）。
- T=4096 时，CTAS=4 的无通信 GEMM 链与默认相同（132.2 对 132.3 ms）。因此它的 9.4 ms 收益全部来自 chain_overhead（16.5 减至 7.2 ms），GEMM 本身没有变快。

## 未验证的假设

1. nsys 只在 T=1024、默认 CTAS 下做过，且只有 rank 0。CTAS=4 带来 T=4096 收益的机制只是推测（AG 占用的 SM 较少，因此 GEMM 被拖慢得少），没有 trace 支持。
2. AG 时长包含等待其他 rank 的时间，因此“时长增量”可能偏高。单 rank trace 无法拆分。
3. GEMM 核时间增加 27% 归因于同时运行的 AG（共享 SM 或带宽）。这是把同配置下重叠 rank 与 gemm_alone 的 nvjet 时间比较得到的，假设两者用了相同的 cuBLAS kernel。没有 SM 占用计数器来直接确认。
4. carveout 会为 NCCL 留出 SM，未直接验证。AG 启动进度只从 0.89 变到 0.86，说明它没有释放出预期的 SM，但 SM 占用本身没有测量。
5. 用 nvjet kernel 代表 GEMM。gelu 和逐元素 kernel 没有计入。
6. NCCL 版本：`sysinfo.txt` 中的环境变量为 `NCCL_VERSION=2.23.4-1`，而 torch 报告 NCCL 2.30.7。没有 NCCL_DEBUG 日志，无法确认实际加载的库。
7. 统计：sweep 为 10 次重复，nsys 为 3 次重复（每标签 48 个 AG）。rep 间 sd 为 0.2–1.3 ms，因此小于 0.5 ms 的差异（如 CTAS=16 在 T=1024 的 −0.2 ms）不作结论。
8. 没有跨 rank 的离散度数据。JSON 只保存各 rank 的最大值，原始数据只有 rank 0。
9. 继承自 `e1_nsys_ready.py` 的假设：CUDA_EVENT 完成时间由 trace 推算，因为其 timestamp 全为 0。我用原生 SQL 核对了 2 个 AG 的启动时间、时长、启动时的 GEMM 状态以及前一个 AG 的结束时间。事件等待得到的 ready 时间没有独立核对。
10. 结果只来自单节点 8 卡，不能直接外推到 E1 的跨节点 IB 场景。
